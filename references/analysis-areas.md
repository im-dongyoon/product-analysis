# 영역별 수집 항목

각 영역: 모을 것 / 어디서 / 다 됐다고 볼 기준.

## A. 회사·사업
- 모을 것: 운영사 법인명, 대표, 설립·출시일, 투자 단계·금액·투자사, 인원 규모, 고객군, 수익 구조(구독, 건당, 수수료, 광고), 요금제 표 원문(플랜별 한도·기능 차이·연간 할인·부가세 표기), 무료 한도, 환불·해지 규칙.
- 어디서: 서비스 푸터 사업자 정보, 공정위 사업자 정보 조회, DART(외부감사 대상이면 감사보고서: 매출·인원), 공식 보도자료, 더브이씨·혁신의숲·Crunchbase [2차], KIPRIS(상표: 서비스명·출원일, 특허: 기술 방식과 화면 흐름 도면), 이용약관, 가격 페이지.
- 기준: 요금제 표가 원문 그대로 있고, 돈 버는 지점(어떤 행동에서 결제가 일어나는지)이 화면 근거와 함께 적혀 있다.

## B. 화면 목록
- 모을 것: 모든 화면을 화면ID(S01…)·이름·URL 패턴·권한(비로그인/로그인/유료/관리자 추정)·진입 경로로. 같은 틀의 화면(상세 페이지 등)은 하나로 묶고 개수만 적는다. 모달·바텀시트·토스트도 화면ID를 준다.
- 어디서: 메뉴·푸터, `sitemap.xml`, `robots.txt`, `llms.txt`, `page-inventory.js`의 `internalLinks`를 따라 넓히기, 검색엔진 `site:` 결과, 앱 화면.
- 기준: 메뉴·사이트맵·링크에서 나온 URL 패턴이 전부 목록에 있다. 트리로 그린 화면 지도가 있다.

## C. 화면별 명세 (화면ID마다)
- 모을 것: 영역 구성(위→아래 블록 순서와 각 블록의 역할), 상태별 캡처(기본·빈 상태·로딩·오류·성공·권한 없음·한도 초과), 문구 원문 전부(버튼, 안내, 빈 상태, 오류, 토스트, 툴팁), 입력 칸 규칙(필수, 길이, 형식, 선택지, 기본값, 클라이언트 오류 문구), 상호작용(누르면 무엇이 열리는지, 정렬·필터·페이지 넘김 방식, 무한 스크롤 여부), 연결된 API(H의 번호).
- 어디서: 직접 써 보기, `page-inventory.js`, `api-capture.js`.
- 기준: 화면마다 PC·모바일 캡처와 위 항목이 표로 채워져 있다.

## D. 사용자 흐름
- 모을 것: 흐름별 단계 표(화면ID, 사용자 행동, 시스템 반응, 분기 조건), 단계 수·클릭 수, 가입·결제 벽 위치, 이메일·문자·푸시가 오는 시점(가입한 경우 실제 받은 메일 제목·발신 시각).
- 기본 흐름: 첫 방문 → 가입·로그인(소셜 로그인 종류) → 온보딩 → 핵심 행동 → 결과 → 다시 오게 하는 장치 → 결제 → 설정·알림 → 해지·탈퇴 화면(누르지 않고 화면과 문구만).
- 기준: 흐름마다 시작부터 끝까지 빈 단계 없이 이어진다.

## E. 기능 규칙
- 모을 것: 숫자 한도(글자 수, 파일 크기·형식, 횟수), 계산 규칙(가격 계산, 할인, 점수), 정렬·추천 기준(관찰한 결과로 추정), 알림 규칙, 권한·역할(팀 기능이면 역할별 가능한 일), 상태값(진행 중, 완료 등 화면에 나오는 상태 전부와 바뀌는 조건).
- 어디서: 관찰, 도움말·FAQ, 약관, API 응답의 상태 필드.
- 기준: 규칙마다 근거(화면 문구 원문 또는 API 필드)가 붙어 있다.

## F. 디자인 시스템
- 모을 것: 색(글자·배경·테두리, 쓰임별), 글꼴·글꼴 파일, 글자 크기 단계(크기/줄 간격/두께 조합), 간격 단계, 모서리, 그림자, 콘텐츠 최대 너비, @media 기준, 다크 모드 여부, 아이콘 방식, 움직임(전환 시간·곡선, 로딩 표시), 컴포넌트 목록(버튼 종류별 크기·색·상태, 입력 칸, 카드, 탭, 모달, 토스트, 표)과 각 상태(기본·마우스 올림·누름·비활성·오류).
- 어디서: `design-tokens.js`를 대표 화면 3곳 이상 × PC·모바일, 다른 출처 CSS 파일, 컴포넌트 캡처.
- 기준: 숫자 값 표 + 컴포넌트별 캡처. 사용 횟수가 적은 값은 예외로 따로 표시.

## G. 기술 스택·인프라
- 모을 것: 프론트 프레임워크, 렌더링 방식(서버 렌더링 여부: HTML 원문에 본문이 있는지), 호스팅·CDN(응답 헤더 `server`·`x-vercel-id`·`cf-ray`·`x-amz-cf-id`), 분석·광고·채팅·오류 감시·결제·로그인 도구, 하위 도메인(app·api·admin·staging 등), 메일 발송 서비스, 앱이면 앱 정보(크기, 최소 OS, 권한).
- 어디서: `detect-stack.js`, `fetch(url)` 응답 헤더, DNS(`https://dns.google/resolve?name=<도메인>&type=MX` / `TXT`: SPF에 sendgrid·mailgun·amazonses 등), 인증서 기록 `https://api.certspotter.com/v1/issuances?domain=<도메인>&include_subdomains=true&expand=dns_names`(하위 도메인 목록만. crt.sh는 502가 잦다), 채용 공고(원티드·로켓펀치·자사 채용 페이지의 기술 스택), 기술 블로그·발표, 개인정보처리방침의 처리위탁·국외이전 업체 목록(쓰는 클라우드·메시지·결제 업체가 공식으로 나온다).
- 기준: 도구마다 단서(파일 주소, 전역 변수, 헤더, 공식 문서)가 붙어 있다.

## H. API·데이터 구조
- 모을 것: API 목록(번호, 방법, 경로 패턴, 쿼리·본문 키, 응답 모양, 어느 화면·행동에서 나가는지, 페이지 넘김 방식), 실시간 방식(WebSocket·SSE·폴링), 엔티티 목록과 필드·자료형·상태값, 엔티티 사이 관계(ERD를 mermaid로), 개인정보처리방침 수집 항목과 맞춰 본 결과.
- 어디서: `api-capture.js`, 화면 표시 값, `__NEXT_DATA__` 같은 페이지 내장 데이터, 개인정보처리방침.
- 기준: 핵심 흐름의 모든 화면 행동에 API가 연결돼 있다. 필드마다 [사실](응답에서 봄) / [추정](화면에서 추정).

## I. 유입·성장
- 모을 것: 사이트맵 규모와 유형별 개수, 메타·구조화 데이터, `llms.txt`, 콘텐츠 유형과 발행 빈도, 브랜드 검색량(네이버 키워드 도구, 읽기만), 광고 문구(Meta 광고 라이브러리, Google 광고 투명성 센터), 공유·초대·추천 보상, 다시 오게 하는 장치(알림, 이메일, 저장, 연속 사용 보상), 트래픽 추정 [2차].
- 기준: 유입 경로별 근거 화면이 있다.

## J. 운영
- 모을 것: 고객센터 채널과 운영 시간, 상담·전문가 연결 방식, 처리 소요 안내 문구, 사람이 개입하는 지점(검수, 배정, 승인 대기 상태로 추정), FAQ 목록.
- 기준: 화면에 드러난 운영 단계마다 [추정] 표시와 근거 문구.

## K. 사용자 반응
- 모을 것: 평점·리뷰 수(확인 날짜), 많이 나온 불만·칭찬(직접 센 개수/본 리뷰 수), 원문 인용과 링크.
- 어디서: 앱스토어·플레이스토어, 네이버 카페·블로그 후기 원문, 디스콰이엇, X, Reddit, Product Hunt, G2.
- 기준: 리뷰 30개 이상(있다면)을 직접 읽고 센 표.

## L. 변화 이력
- 모을 것: 메인·가격 페이지의 시기별 변화(메인 문구, 요금, 메뉴), 기능 추가 순서, 앱 버전 기록.
- 어디서: `http://web.archive.org/cdx/search/cdx?url=<도메인>&output=json&fl=timestamp,original&collapse=timestamp:6` 로 월별 시점을 뽑고 몇 개 시점만 연다, 업데이트 내역, 앱스토어 버전 기록, 보도자료.
- 기준: 시점별 표(날짜, 바뀐 것, 근거 URL).

## M. AI 기능 (해당 시)
- 모을 것: 입력 형식(글, 파일, 음성), 답 형식(마크다운, 카드, 표, 버튼), 생성 중 진행 문구 원문 전부와 순서, 스트리밍 방식(SSE·WebSocket, 응답 조각 모양), 출처 표시 방식, 후속 질문 제안, 거절·한도 메시지 원문, 비로그인 한도(몇 번째 질문에서 막히는지 세기), 대화 저장·공유, 모델 단서(약관·도움말·응답 필드).
- 기준: 서로 다른 유형 질문 3개 이상으로 같은 화면 상태를 반복 확인했다.
- 튜토리얼·데모는 각본 시연일 수 있다. `api-capture.js`로 AI API 호출이 있는지 보고, 없으면 실제 프로젝트를 따로 만들어 비교한다(2026-11 매니패스트: 튜토리얼과 실제 생성 순서가 달랐다).
- 생성 결과 응답에 `aiModel`, `tokenUsage` 같은 필드가 있는지 본다. 모델명과 비용 구조의 1차 근거다.
- 크레딧·사용량 과금이면 단계마다 잔액 API나 화면 잔액을 재서 기능별 비용을 표로 남긴다. 무료 한도가 작으면 비싼 기능부터 쓰지 말고 핵심 흐름 순서대로 쓴다.
